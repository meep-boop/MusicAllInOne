# Critical Review of the DrumScore Technical Plan

## TL;DR
- **alphaTab is the correct core engine — keep it.** No other JS library combines native Guitar Pro 3–8 import, real drum-staff notation, a bundled multi-track SoundFont synth, an editable score model, and SVG bounds for overlays. The realistic alternatives (OSMD, VexFlow, Verovio, abcjs) each fail at least one load-bearing requirement, usually GP import or built-in playback.
- **Stay a browser-local web app for Stages 0–4; wrap in Tauri only when Stage 5 (mic) becomes the focus.** alphaTab runs in both Tauri and Electron, but a plain Vite/TS PWA is the lowest-friction path and loses almost nothing for personal use. Tauri (not Electron) is the right wrapper if/when you want OS keychain storage, reliable file-library access, and cleaner mic permissions.
- **Stage 5 should ship as onset-only score following, not "which drum did I hit."** Single-mic onset detection in the browser is mature and accurate (>85% F-measure on solo drums); full drum classification from one room mic is a research-grade problem with no off-the-shelf in-browser model. Build the "confirm a hit near the expected time" follower and explicitly defer classification.

## Key Findings

### Goal 1 — alphaTab vs. the field
- alphaTab is **actively and heavily maintained by a single primary author (Daniel Kuschny, "Danielku15")**. The npm package `@coderline/alphatab` is at **v1.8.3** (confirmed on npm, "last published 13 days ago" as of June 2026), with v1.9.0 issues open as of late December 2025. It is MPL-2.0, has **4,199 GitHub stars per the npm registry page (npmjs.com/package/@coderline/alphatab)**, and has been developed since 2010.
- It is the **only realistic option that imports Guitar Pro 3–8 natively** AND renders proper drum notation AND ships a synth. Per alphaTab's official Guitar Pro 8 format docs (alphatab.net/docs/formats/guitar-pro-8): *"Compatibility Level: Mature and well tested (through GP7) … Number of total supported features: 96% (110/114) … Number of relevant supported features: 96% (98/102)."*
- Drum/percussion notation has been a **first-class feature only since v1.4 (2023)**; it uses the Guitar Pro 5 drum-tab model, supports multiple voices, ghost notes, accents, and articulations (kick, snare, hi-hat open/closed/foot, ride, crash, cross-stick). There have been **specific drum bugs**, e.g. "Broken percussion articulations for some GP5 files" fixed in the v1.8 line, and GP-export of percussion articulations was wrong until fixed in v1.5.
- The **bundled synth (alphaSynth)** is based on TinySoundFont/SFZero and ships the **Sonivox SF2** soundfont (Apache-2.0, the Android system soundfont). It plays guitar+bass+drums together with per-track volume/pan/mute. Quality is "decent" but not premium; SF3 (Ogg Vorbis) support is experimental as of v1.4.
- The **`boundsLookup` API is real and load-bearing-capable** but has rough edges: `boundsLookup.findBeat(beat)` returns beat bounding boxes for overlays, but there is no bounds API for tempo/time-signature glyphs, and snapping to bar/measure boundaries is awkward (open issue #2394).
- The **Score model is editable but the docs explicitly warn against naive mutation**: "Direct modification of this data model is usually not easily possible … some modifications might break the rendering pipeline."

### Goal 2 — Web app vs. native
- alphaTab **runs in both Tauri and Electron**, but both needed environment-detection workarounds; Electron support was explicitly improved in v1.6.
- **Microphone access via getUserMedia works in Tauri but has documented macOS friction** (double permission prompts, `navigator.mediaDevices` undefined without Info.plist entries, permissions not remembered). On Windows (the user's platform, a Dell XPS) WebView2 is Chromium and behaves like Chrome.
- **Tauri ships 2–10 MB installers / ~50 MB RAM; Electron ships 80–200 MB / 120 MB+ RAM** (per PkgPulse's 2026 benchmark guide, pkgpulse.com, in identical todo-app benchmarks). As a concrete real-world data point, Hoppscotch's Electron→Tauri migration cut the bundle *"from 165 MB to 8 MB and a 70% reduction in memory usage"* (tech-insider.org, "Tauri vs Electron 2026"). Tauri uses the OS WebView (WebView2 on Windows); Electron bundles Chromium.
- **API-key storage**: browser localStorage is plaintext; Tauri offers OS keychain via the `keyring` crate (Stronghold is being deprecated in v3).

### Goal 3 — Single-mic onset detection & classification
- **Onset detection is mature and accurate.** Percussive/solo-drum onset detection scores **>85% F-measure at ±50 ms** in MIREX-era evaluations. Frame/hop sizes of 512/256 at 44.1 kHz give ~11.6 ms / 5.8 ms resolution — fine enough to resolve 16th notes at 160 BPM (~40 ms spacing).
- **Best browser libraries: Essentia.js** (WASM port of Essentia; exposes `SuperFluxExtractor` and `OnsetDetection`, confirmed to run in an AudioWorklet) and **Meyda v5.6.3** (computes `spectralFlux`; default 512-sample buffer; you supply the peak-picker). **aubiojs (WASM port v0.2.1, last published Nov 2022) does NOT expose onset detection** — only Tempo/Pitch/FFT per its npm/GitHub release listing — despite the underlying C library having it.
- **Drum classification is research-grade.** The best open ADT package, ADTOF (CRNN), hits ~0.89 F-measure on MDB drums for 5 classes but **drops to ~0.63 on harder real-world data (RBMA)** — attributed to Zehren, Alunno & Bientinesi, "High-Quality and Reproducible Automatic Drum Transcription from Crowdsourced Data," *Signals* 2023, 4, 768–787 (repo MZehren/ADTOF, CC BY-NC-SA 4.0). Hi-hat/cymbal confusion is the dominant error.
- **No pretrained drum-ADT model runs fully client-side today.** ADTWeb is server-side; Magenta's TF.js Onsets-and-Frames port is piano-only (OaF-Drums was never ported); ADTOF/ADTLib are Python-only. A browser drum-ADT would require custom ONNX Runtime Web/TF.js conversion plus Essentia.js mel-spectrogram preprocessing — feasible but unproven publicly.

## Details

### GOAL 1: Is alphaTab the best notation+playback engine?

**Verdict: Yes, decisively, for this exact use case. Keep it.**

The requirement set — (a) import Guitar Pro 3–8, (b) render standard drum-staff notation with ghost notes/accents/tuplets/odd meters, (c) play all tracks (guitar+bass+drums) through a built-in synth with a live cursor and per-track mix, (d) expose an editable note model, and (e) expose SVG bounds so you can position overlays — is uniquely satisfied by alphaTab. No competitor meets even three of these five without bolting together multiple libraries and writing a Guitar Pro parser yourself.

**Maintenance & licensing.** `@coderline/alphatab` is at v1.8.3 on npm (last published ~13 days before June 2026), with active v1.9.0 development through December 2025. It has been developed since 2010, has 4,199 GitHub stars per the npm registry page, and is released under MPL-2.0. The MPL-2.0 implication for you is benign: MPL is file-level copyleft. You can use alphaTab in a closed or personal app freely; you only have to publish modifications **to alphaTab's own source files** if you distribute them. Since you'll consume it as an npm dependency and write your app code in separate files, you have zero copyleft obligations for a personal, non-distributed app. The single-maintainer "bus factor" is the main long-term risk, partly mitigated by the .NET/Kotlin commercial flavors funding ongoing work.

**Drum notation quality.** This is the area to scrutinize, and it's genuinely good but young. Percussion was added as a first-class feature only in **v1.4 (2023)**; alphaTab "uses the same drum tab notation as Guitar Pro 5" and hides the guitar-tab staff for percussion tracks. It supports a percussion clef, multiple drum voices per staff, ghost notes, accents, and a full articulation set (KickHit, SnareHit, HiHatOpen/Closed/Foot via pedal-hat articulations, Ride, RideBell, Crash, cross-stick, toms). It also separates the *displayed* notehead from the *played* MIDI key (important for `x` noteheads on cymbals). Because percussion is recent, there is a non-trivial history of drum-specific bugs: "Broken percussion articulations for some GP5 files" (fixed in the v1.8 line), wrong articulation export to GP (fixed v1.5), and the v1.8 regression where clef thresholds mis-rendered. None are blocking, but **you should pin a recent version (≥1.8.3) and test your actual GP library's drum tracks early.**

**Guitar Pro import reliability.** alphaTab's GP support is its oldest and most mature subsystem. GP6 (.gpx), GP7 (.gp), and GP8 (.gp) are all zip/XML containers reading the same `score.gpif`; per the official format docs GP8 is *"Mature and well tested (through GP7) … 96% (110/114)"* of total features. Known gaps are mostly cosmetic/automation (e.g. progressive tempo transitions are flattened — `tempoAutomation.isLinear` always true; GP8 backing-track audio is partially supported). For drum tracks specifically, the main historical issues were the GP5 percussion-articulation bugs above. This is materially better than any alternative — **no other JS library imports GP8 at all.**

**Bundled synth.** alphaSynth converts the Score → MIDI → audio via a TinySoundFont/SFZero-derived engine, fed by the bundled **Sonivox SF2** (the Android system soundfont, licensed Apache-2.0 by Google from Sonic Network Inc.). The maintainer calls Sonivox "one of the best free soundfonts I could find … small but decent." It plays multiple tracks simultaneously with per-track volume/pan/mute and tempo/transpose control, which is exactly your play-along requirement. Quality is "GM-decent," not sample-library realism — acceptable for a practice backing track. For your Stage 4 sound-pack swap, `api.loadSoundFont(data, append)` lets you load multiple/replacement SF2 files at runtime; note **alphaTab's SF2 path requires uncompressed PCM samples**, and a full GM soundfont with good sound is rarely under ~10 MB, so per-genre packs will be the largest assets you ship. SF3 (Ogg-compressed) is supported but flagged experimental with CPU-cost caveats for sample decode.

**boundsLookup / overlay positioning.** This works and is the documented approach ("use the boundsLookup … obtain any position of beats, bars and masterbars and place custom overlays"). `api.renderer.boundsLookup.findBeat(beat)` returns a beat's bounding box; you draw R/L sticking letters, your edit cursor, and the mic cursor as absolutely-positioned DOM/SVG over the `.at-viewport`. **Caveats you must design around:** (1) there is no bounds API for non-note glyphs like tempo/time signatures (developers resort to scraping SVG elements with class `at`); (2) snapping overlays/loop handles precisely to *bar* boundaries is awkward and is an open issue (#2394); (3) bounds are invalidated on every re-render/resize, so you must recompute overlays on the `renderFinished` event. For your three overlay use cases (sticking letters under noteheads, an edit caret, a play cursor) the per-beat bounds are sufficient — but budget time for the resize/re-render bookkeeping.

**Editing the Score model (Stage 2 risk).** This is the second area to scrutinize. alphaTab's data model (Score → Track → Staff → Bar → Voice → Beat → Note, plus MasterBars holding time/key signatures across all tracks) is fully exposed and *can* be mutated in code, after which `api.render()` relayouts and regenerates MIDI. The official docs, however, explicitly warn: *"Direct modification of this data model is usually not easily possible … while some modifications might be possible and are reflected after re-rendering, others might fully break the rendering pipeline due to inconsistencies."* Practically: the importers do a lot of consistency wiring (e.g. `removeNote` once left a dangling `stringLookup` reference, since fixed). **Your "command layer that mutates the same Score" architecture is sound, but you will need to call internal `finish()`/consistency steps and re-render, and you should expect to discover undocumented invariants by trial.** A pragmatic alternative for Stage 2 that sidesteps most of this: have your editor emit **alphaTex** (alphaTab's text input format, which since v1.4 fully supports percussion, voices, tuplets, time signatures, ghost notes, accents) and re-parse, rather than surgically mutating the live object graph. This trades fine-grained edit performance for robustness and is worth prototyping both ways.

**The alternatives, and why each loses:**
- **OpenSheetMusicDisplay (OSMD)** — renders MusicXML via VexFlow, actively maintained, has a cursor and improving percussion support (cajon options, percussion one-line cutoff, drum notehead handling). But it **does not import Guitar Pro**, **has no built-in synthesizer** (you'd bolt on a separate sampler), and has documented drum-notation gaps (open/closed hi-hat `+`/`o` and accent placement not fully respected — issue #887; percussion noteheads — issue #325). You'd be writing a GP→MusicXML pipeline and a multi-track synth yourself. Net: more work, worse fit.
- **VexFlow** — a *rendering engine only* (TypeScript, MIT, v5.0.0, actively maintained). It does support percussion noteheads, but it has **no importer (no GP, no MusicXML), no playback, no audio, and no layout/formatting beyond what you compute.** It's the layer *under* OSMD. Using it directly means building the entire model, importer, synth, and engraver — strictly more work than alphaTab.
- **Verovio** (RISM, MEI/MusicXML/Humdrum engraving, open source) — excellent, scholarly-grade engraving and supports percussion clefs/noteheads. But it is **engraving-focused with no built-in interactive multi-track synth playback** (it can emit MIDI, but you wire your own player), **no Guitar Pro import**, and is heavier (WASM toolkit). Better for musicology/publishing than an interactive play-along trainer.
- **abcjs / ABC notation** — used by GrooveScribe for drum grooves, has rudimentary synth playback. But ABC is a poor fit for full multi-track band scores, **no GP import**, and drum support is convention-hacked rather than first-class. Fine for tiny grooves, wrong for importing real songs.
- **Soundslice** (commercial, not a library) — worth studying as a design north-star (it's the best-in-class "living sheet music" play-along, and reportedly built its own renderer). Not usable as a free dependency.
- **flat.io** — embed/API is a hosted commercial product, not a self-hostable free library; off the table for a free local app.
- **Purpose-built drum-notation libraries** — there is no maintained JS *library* dedicated to drum notation. GrooveScribe (abcjs-based) and desktop apps (MuseScore, Musink, Aered, Beat Note) exist as *applications*, not embeddable engines. This confirms alphaTab is the only library-grade option that does drums + import + playback.

**One concrete risk to log:** alphaTab spawns Web Workers and Audio Worklets from its own script files; with Vite you **must** use the official `@coderline/alphatab` Vite plugin (it copies the bundled Bravura font + SONiVOX soundfont to `/font/` and `/soundfont/` and wires the worker/worklet entry points). This is already implied by your stack but is the #1 integration footgun.

### GOAL 2: Browser-local web app vs. native (Tauri/Electron)?

**Verdict: Build Stages 0–4 as a plain browser-local web app (ideally an installable PWA). Adopt Tauri — not Electron — only when you start Stage 5 in earnest, and only if you hit a concrete browser limitation.**

**Does alphaTab run in the wrappers?** Yes in both. alphaTab is "web-first" and runs in any modern ES6 browser, so it runs unchanged in WebView2 (Tauri/Windows) and Chromium (Electron). Both wrappers historically tripped alphaTab's environment detection — Electron injects Node globals into the renderer, which made alphaTab wrongly think it was in Node and refuse to start `AlphaTabApi`; this was explicitly improved in **v1.6** ("we now better detect if we're running in a browser window allowing easier usage in Electron apps"), and an Obsidian (Electron) plugin author documented a working sandbox workaround. The web-worker/audio-worklet/soundfont machinery works in both as long as your bundler is configured with alphaTab's plugin. **No blocker either way.**

**Microphone (the only thing that should drive you native).** In a plain browser on Windows, `getUserMedia` + AudioWorklet is reliable and well-trodden — and you're on a Dell XPS, where the browser path is excellent. So for Stage 5, a browser app is *already viable*. The native question is about polish, not capability:
- **Tauri on Windows = WebView2 (Chromium)**, which behaves like Chrome for getUserMedia — the smoothest case.
- **Tauri on macOS = WKWebView**, which has a documented history of mic friction: double permission prompts (app-level + webview-level), `navigator.mediaDevices` being undefined without `NSMicrophoneUsageDescription` in Info.plist, and permissions not being remembered across launches (Tauri/wry issues #1195, #10898, #8979). Since you're on Windows, this is largely irrelevant to you personally.
- **Electron = bundled Chromium**, so mic behavior is identical to Chrome everywhere, at the cost of bundle size.

**Audio latency for mic-follow.** There is no meaningful low-level audio-latency advantage to a webview wrapper: Tauri and Electron both run your audio through the *same* Web Audio API / AudioWorklet as the browser, so input latency is governed by the OS audio stack and the AudioContext, not the wrapper. A true latency win would require bypassing Web Audio entirely with a native (Rust/CPAL or C++) audio thread and IPC-ing results to the UI — which is a large amount of extra complexity that **is not justified** for a personal practice tool whose follower only needs ~10–30 ms onset resolution (well within Web Audio's reach). Conclusion: **going native does not improve mic latency unless you also rewrite the audio capture in native code, which you should not do.**

**File handling.** This is the strongest *pro-native* argument. In the browser, a persistent local song library means either the **File System Access API** (Chromium-only, requires per-session permission grants, clunky for a managed library) or stuffing files into IndexedDB (your current plan — fine, but files live inside the browser profile, not as real files on disk). Native (Tauri `fs`/`dialog` plugins or Electron) gives you **direct, permission-free access to a real folder of `.gp` files and `.sf2` packs**, which is a materially nicer experience for a local library and for swapping in large soundfonts. If the "song library + sound-pack folder" experience starts to annoy you, that's the trigger to wrap in Tauri.

**API-key storage.** Your plan stores the OpenRouter key in localStorage. For personal use on your own machine this is acceptable, but it is plaintext in the browser profile. Native is meaningfully better here: **Tauri can store the key in the OS keychain via the `keyring` Rust crate** (Windows Credential Manager / macOS Keychain / libsecret). Note Tauri's older **Stronghold** plugin is being deprecated and removed in v3, so prefer `keyring`. Electron has `safeStorage`. This is a real but minor benefit — for a single-user local app the practical risk of localStorage is low.

**Bundle size & build complexity (Tauri vs Electron).** Per PkgPulse's 2026 benchmarks, Tauri ships **2–10 MB installers and ~50 MB RAM** by using the OS WebView; Electron ships **80–200 MB and 120 MB+ RAM** by bundling Chromium. As a real migration data point, Hoppscotch's Electron→Tauri move cut its bundle "from 165 MB to 8 MB and a 70% reduction in memory usage." Tauri's cost is a Rust toolchain and per-platform WebView variance (WebView2 vs WKWebView vs WebKitGTK render slightly differently); Electron's cost is bloat but with rock-solid Chromium consistency. For a **single developer on Windows building for personal use**, Tauri's downsides (cross-WebView testing) barely apply — you're testing on one WebView2 target — while its upsides (tiny binary, native fs, keychain, clean Windows mic) all land. **If you go native, go Tauri.** Electron is only worth it if you needed deep Node ecosystem integration or guaranteed identical cross-OS rendering, neither of which you do.

**What you lose by staying web:** real-file library ergonomics, OS-keychain key storage, and a double-click desktop icon (recoverable via PWA install). What you gain: zero native toolchain, fastest iteration, trivial deploy. **Recommended staging: ship Stages 0–4 as an installable PWA; when you begin Stage 5, evaluate Tauri specifically for the file-library and key-storage wins, and adopt it then.** This avoids native complexity "unnecessarily," exactly as requested, while keeping the door open.

### GOAL 3: State of the art for single-room-mic drum onset detection & classification

**Verdict: Build the onset-only score follower. It's achievable and will work well. Treat "which drum" classification as an explicit research-grade stretch goal that almost certainly cannot be done reliably in-browser from one room mic in 2026.**

**(a) Onset detection — solidly achievable.** The good news is that detecting *that a hit happened* is essentially a solved problem for percussive single-mic audio. In MIREX-era evaluations, the solo-drums onset class scores **>85% F-measure at the standard ±50 ms tolerance**, with spectral-flux methods (Böck's SuperFlux/ComplexFlux) among the top performers. Plain spectral flux on general pitched material is lower (~74–76%), but drums are the easy case because transients are sharp.

The mechanics: compute a short-time spectral flux (or high-frequency content / complex-domain) onset-detection function, apply an adaptive (moving-average) threshold, and peak-pick. At 44.1 kHz with a 1024-sample window / 512-sample hop you get ~23 ms frames at ~11.6 ms spacing; dropping to a 256-sample hop gives ~5.8 ms resolution. **16th notes at 160 BPM are ~37.5–40 ms apart, comfortably above an 11.6 ms hop**, so the resolution is adequate for fast drumming — the practical risks are (1) minimum inter-onset-interval guards merging very close hits (tune this down), and (2) timing jitter near the tolerance boundary, not raw resolution.

**Library recommendation, concrete:**
- **Essentia.js** (MTG/UPF, WASM port of Essentia, AGPLv3/proprietary dual license — check licensing for your use) is the most production-credible browser option. It exposes `SuperFluxExtractor` (Böck SuperFlux) and a general `OnsetDetection` algorithm (HFC/complex/flux/melflux/rms methods) plus an `Onsets` peak-picker, and it is **confirmed to run inside an AudioWorklet** (the docs ship an `essentia-worklet-processor.js` real-time example). AudioWorklet support is "latest Firefox and Chromium-based browsers."
- **Meyda v5.6.3** (MIT) computes `spectralFlux`, `energy`, `rms`, `complexSpectrum`, etc., default 512-sample buffer (~11.6 ms). It does **not** ship a peak-picker — you write the adaptive threshold yourself. Lighter-weight than Essentia.js, good if you want a small dependency and control.
- **Avoid aubiojs** for this: the WASM port (`aubiojs` v0.2.1, last published Nov 2022, unmaintained) **only exposes Tempo/Pitch/FFT and does NOT expose aubio's onset detector**, despite the underlying C library having excellent onset detection. This is a common trap.
- Reference open-source browser onset code: **Keavon/Web-Onset** (spectral-flux + adaptive threshold + peak-picking in Web Audio, for rhythm games) and **chrisguttandin/web-audio-beat-detector** (tempo-oriented). For an embeddable C core that could be WASM-compiled, **michaelkrzyzaniak/Beat-and-Tempo-Tracking** is causal real-time spectral-flux onset+beat tracking in ANSI C.

**(b) Drum classification — research-grade, defer it.** Telling *which* drum was hit (kick/snare/hi-hat/toms/cymbals) from one room mic is Automatic Drum Transcription (ADT), and the state of the art is good in the lab but not packaged for your context:
- The leading open package, **ADTOF** (MZehren/ADTOF, a CRNN; log-mel input, 2048/441 STFT ≈ 100 Hz frames; CC BY-NC-SA 4.0), reaches **~0.89 F-measure for 5 classes on MDB-Drums and ~0.85 on ENST, but only ~0.63 on the harder RBMA real-world set** (Zehren, Alunno & Bientinesi, "High-Quality and Reproducible Automatic Drum Transcription from Crowdsourced Data," *Signals* 2023, 4, 768–787). A 2025 extension (Riley & Dixon) adds source separation to push to 7 classes (open/closed hi-hat, ride/crash split) plus velocity. The dominant error everywhere is **hi-hat↔cymbal and similar-instrument confusion** — exactly the distinctions a drummer cares about.
- Crucially for you: **these are offline, Python/TensorFlow/madmom pipelines.** ADTLib is Python-only; ADTOF is Colab/Python; Magenta's **Onsets-and-Frames was ported to TF.js for piano only — OaF-Drums (trained on the 444-hour E-GMD dataset) was never ported.** ADTWeb, the "browser version of ADTLib," is actually **server-side** (it uploads audio to a BCU server). **There is no published, working, fully client-side drum-ADT model.** A browser implementation would mean converting a unidirectional CRNN to ONNX Runtime Web / TF.js and doing mel-spectrogram preprocessing via Essentia.js — feasible in principle, unproven in practice, and a large project on its own.
- The simple band-energy heuristic in your plan (kick = low band, snare = mid + noise, cymbals = high band) is a **reasonable coarse first pass** and will distinguish kick from cymbal fairly well, but it will **struggle exactly where it matters** — snare vs. tom, hi-hat vs. ride vs. crash, and any two simultaneous hits (a single room mic sums everything). Treat it as a "nice-to-have hint," never as reliable transcription.

**(c) Score following — the right framing for Stage 5.** Because you *already have the score*, you do not need open-ended transcription; you need to confirm the player reached an expected position. The literature calls the rigorous version **online time warping (OLTW/DTW)** alignment (e.g. the 2025 open-source **Matchmaker** library for piano; CQT-DTW followers), and HMM/state-space approaches. But for a drum practice tool, the pragmatic and entirely adequate approach is a **rule-based "expected-onset window" follower**: from the known score, compute the next expected onset time(s); when the onset detector fires inside a tolerance window (start ±60–100 ms, tightening as confidence builds) around an expected hit, advance the cursor. This is essentially how gamified trainers (Yousician/Melodics-style) feel responsive without doing full transcription, and it sidesteps the classification problem entirely — you only ask "did *a* hit land near where one was expected?"

**Realistic Stage 5 MVP and what to defer:**
- **Ship:** Essentia.js (or Meyda) spectral-flux onset detection in an AudioWorklet → adaptive-threshold peak-picker → "expected onset within tolerance window" cursor advance. Expect **>85% hit-confirmation accuracy on clean solo-kit audio**, ~10–30 ms detection latency, with tunable tolerance to trade false-positives against missed hits.
- **Optionally prototype:** coarse 3-band energy classification as a low-confidence "looks like a kick/snare/cymbal" hint, clearly labeled as approximate.
- **Defer/drop:** full per-drum transcription, simultaneous-hit disambiguation, and any ML ADT model — these are not reliably achievable from one room mic in-browser today, and attempting them will sink the project.

## Recommendations

1. **Keep alphaTab; pin ≥ v1.8.3 and use the official Vite plugin.** This is the single highest-leverage correct decision in the plan. Immediately test-import your real `.gp` drum tracks to surface any percussion-articulation bugs early.
2. **Prototype Stage 2 editing two ways before committing:** (a) direct Score mutation + re-render via a command layer, and (b) emit-alphaTex-and-reparse. Pick based on which keeps the rendering pipeline stable; the docs' warning about direct mutation is real. Benchmark for edit latency on a long song.
3. **Build the overlay system (sticking letters, edit caret, mic cursor) on `boundsLookup.findBeat`, and recompute on every `renderFinished`.** Don't rely on bar-level snapping; budget time for the resize bookkeeping.
4. **Stay browser-local (installable PWA) through Stage 4.** Use IndexedDB for songs/settings as planned. Keep the OpenRouter key in localStorage for now, but isolate key access behind a small module so you can swap storage later.
5. **When you start Stage 5, adopt Tauri (not Electron).** Trigger conditions: you want a real on-disk song/sound-pack library, OS-keychain key storage (`keyring` crate, not Stronghold), or a desktop icon. On Windows/WebView2 the mic path is clean; skip Electron's 80–200 MB bloat.
6. **Implement Stage 5 as onset-only score following.** Use Essentia.js `SuperFluxExtractor`/`OnsetDetection` (or Meyda `spectralFlux`) in an AudioWorklet; **do not use aubiojs** (no onset API). Ship the "expected-onset-within-window advances cursor" follower first.
7. **Explicitly scope out drum classification.** Optionally add coarse 3-band energy hints labeled as approximate; do not promise per-drum transcription. Revisit only if a client-side ONNX/TF.js ADT model becomes available off the shelf.
8. **Soundfont strategy for Stage 4:** plan for per-genre SF2 packs being your largest assets (a good GM-quality SF2 is rarely < ~10 MB, PCM-only); load via `api.loadSoundFont(data, append)`; consider caching packs in IndexedDB.

**Thresholds that would change these recommendations:**
- If a maintained, pretrained **drum-ADT model shipping for ONNX Runtime Web / TF.js** appears, reconsider adding real classification to Stage 5.
- If alphaTab's single-maintainer cadence stalls (no releases for ~12+ months) or a drum-rendering bug proves unfixable, OSMD+VexFlow+a separate synth+a GP→MusicXML converter becomes the fallback — at substantially higher effort.
- If you ever want **sample-realistic** band playback rather than GM-decent, that pushes you toward larger SF2/SF3 packs or a native audio path — which would then justify the Tauri move earlier.

## Caveats
- alphaTab's percussion support is genuinely young (since v1.4, 2023) and has a real track record of drum-specific bugs; this review is based on changelogs and issue trackers, not on a hands-on test of *your* specific files. Verify with your library.
- The ">85% F-measure on solo drums" figure is from MIREX-era summaries and Dixon/Böck primary work; it characterizes *detection that a hit occurred*, not which drum, and assumes reasonably clean audio — a noisy room or cymbal wash will degrade it.
- ADT accuracy figures (0.89 MDB / 0.63 RBMA) are offline, drum-only-track results from Python research models; real-time in-browser performance on a single room mic would be worse, which is precisely why classification is deferred.
- Tauri/WKWebView mic issues are macOS-specific and mostly irrelevant on your Windows machine, but would matter if you ever distributed to Mac users.
- The "no fully client-side drum-ADT model exists" finding is current as of mid-2026; this is a fast-moving research area and could change.
- alphaTab's `loadSoundFont` SF2 requirement (uncompressed PCM) and the experimental status of SF3 mean sound-pack file sizes are a real design constraint, not a solved problem.
